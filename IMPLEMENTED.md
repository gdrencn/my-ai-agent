## Verification evidence

Current receipts: [validation/V0_1_3_LOCAL.json](validation/V0_1_3_LOCAL.json), [validation/V0_1_3_NATIVE.json](validation/V0_1_3_NATIVE.json).

- **Portable:** 50 checks pass from source and from the standalone paired tester outside the checkout. Covers the grouped menu, return focus, editable/pending/readonly values, colors and NO_COLOR in real PTYs, native API isolation, load/retry/fit identity, MTP sharing/RS/host fixtures, driver unknown/free behavior, successful/failed usage, identity/routing, transactions and protocol compatibility.
- **Native:** 25 checks pass as ordinary sandbox user in an owned mas container using Ubuntu 26.04.1 LTS / Python 3.14.4, official Ollama 0.40.0, llama.cpp b11429 (d81235049) and Codex CLI 0.160.1. Both selected Qwen3 0.6B models show actual GPU weights, q8_0 KV, compute buffers, layer count and whole-card driver data. llama.cpp identified allocation sum was 2452.74 MiB, Ollama 2529.39 MiB at context 32768; these are load-record observations, not complete process VRAM or performance guarantees.
- **Identity/protocol:** both actual Codex /model pickers show only the original model name, without either startup warning. Profile/catalog/public Responses identity matches that name while Ollama keeps its private routing alias. Actual native function selection and replay pass for both small models. Real Codex shell execution/replay additionally passes against a deterministic upstream fixture; this measures protocol execution rather than model competence.
- **Readonly/lifetime:** status does not change token receipts or loading identity. Ollama forced unload remains unloaded after status. llama.cpp enters the configured 5m sleep, repeated status leaves it sleeping, and codex-local wakes it with a new load ID and fresh usage. Pause hides allocations/usage and preserves the accepted boot target. Container restart autostarts the accepted llama.cpp target, with new service UUID, empty old usage, context 32768, valid current allocations, enabled maa.service and inactive official Ollama service.
- **Actual menu:** installed maa driven in a controlling PTY at 20 × 120 and 12 × 50. Grouped local management, model status/refresh/back, Codex readonly fields, nested YOLO editor cancellation, About/exit, green/cyan/gray rendering and terminal restoration pass. Initial standalone driver attempts sent navigation before the new prompt finished drawing and used an unsupported Controller.wait keyword; corrected drivers passed without product changes.
- **Build:** reproducible bytes, Python 3.11 grammar, shell syntax, product/test boundaries, paired versions and checksums verified. The 5m sleep run used the preceding development artifact; subsequent changes only hardened missing/invalid API and usage fields. Exact hashes and final artifact checks are recorded in the local receipt. The first source color assertions inherited TERM=dumb; the test driver now explicitly provides a color-capable PTY and separately verifies NO_COLOR.

MTP initialization/shared-KV and RS handling are validated with primary source and native-format log fixtures, not an actual MTP/recurrent model run. Source checks include Ollama 0.40.0's pinned llama.cpp b11351 and standalone b11429. Both real models lack MTP weights; **native MTP, large-model stability/performance and partial-offload performance remain unaccepted**. Layer percentages describe native reported layer counts, not a proof that every model tensor is in VRAM. Identified allocation logs are initialization snapshots; subsequent allocator changes and unrelated framework/driver allocations are not inferred.

Whole-GPU data was read on an NVIDIA RTX 5090 Laptop GPU through the container's approved WSL GPU access. Other driver families are not implemented; driver failures remain unknown. HF authenticated/restricted repositories and split GGUF downloads have portable/implementation coverage, not complete native acceptance. Upstream installers may resolve different future versions.
